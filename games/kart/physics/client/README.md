# Client physics, the 1:1 port

The kart physics of KnC.exe ported function by function from the reverse under `docs/reverse/CLIENT_PHYSICS_MAP.md` and `docs/reverse/physics/`. Same order of operations, same constants, same clamps, same substeps, nothing improved. The server stays the oracle, this code is what the client runs.

## Layout

Everything in this folder, namespace `KnC::Kart::Client`, C++17, no dependency on the engine. Standalone CMake project, also built by the root solution as `KnCKartClient`. Tests in `tests/`, one program per module, they read the stock client data from `KNC_CLIENT_DATA` (default `<client>/Data`) and exit 0 when the folder is missing, the replay test reads the recordings folder the build passes as `KNC_RECORDINGS_DIR` (the env var of the same name overrides it).

## Rules

- Function names are the Ghidra names, snake case, `car_physics_tick_local`, `body_integrate`, `world_bsp_locate_point`
- A struct field is named by its meaning and its comment carries the offset written as `car 0x3244`, never with a plus sign
- Every constant is a named `constexpr float` in `constants.h` with its address in the comment, `// 0x5A69A8 speed to km per hour`
- Comments are one line, at most 20 words, only letters digits space @ % - " and '. No em dash anywhere
- Where the docs say guess or leave a question open, port what is written and add `// TODO open <doc> <item>` on that line
- A test proves a module against the real data, the .col of Cookie 01, the csv files, the constants, not against invented numbers
- No dependency on the old engine, on bgfx, on the server. Plain C++17 and the standard library
- The port compiles with `cmake -S games/kart/physics/client -B build-kartclient -G "Visual Studio 17 2022" -A x64` then `cmake --build build-kartclient --config Release`

`body.h` exports the body layer with `CarBody` (the wrapper), `WheelSet` (the sub object with `WheelObject`, `EngineState`, `WheelTireScratch`), `SpawnCatalogue` (the `.car` block, defaults are default.car) and the functions `catalogue_load_car_file`, `catalogue_apply_setup_overrides`, `catalogue_from_stats`, `body_create`, `body_place_and_probe`, `body_ground_probe_response`, `body_apply_force`, `body_integrate`, `body_step_world`, `body_finalize_wheels`, `body_wheels_on_ground_count`, `body_apply_durability_scale`, `body_set_mass_friction`, `body_set_tire_grip`, `gear_wheel_force_solve`, `gear_tire_force_model`. `CarBody::referenceOrientation` and `WheelSet::orientationQ` are the same client memory, the body syncs them at every entry and exit.

`stats.h` exports `KartStats` (17 base floats and 17 bonus floats), `KartStatIndex`, `stat_total`, `TrackTuning` (the three floats of the 0xC3 record and the fall off timeout), `stat_bonus_add_part`.

The stat numbering is the WIRE index, settled on the bytes 2026-09-15 (`physics/INPUT_AND_STATS.md` "The 17 stats, wire numbering, settled"): `car_apply_kart_loadout` 0x490A70 copies the 0xC0 record from its byte 0 to car+0x33A4, so the record stat block at 0xA4 lands at car+0x3448 and wire float k is car+0x3448 plus 4 k with its part bonus at car+0xA7940 plus 4 k. `KartStatIndex` counts that way (MaxSpeed 1, SteeringGain 2, MiniTurboTargetSpeed 3, BoostLeanLift 4, TurnForce 5, WheelSpin 6, WheelSteerAngle 7, DriftChargeRate 8, DriftSteer 9, MiniTurboThreshold 10, MiniTurboHoldTime 11, Grip 12, 13 no reader, CameraDistance 14, CameraPitch 15, CameraHeight 16, BodySetupInput 0), every read in the port goes through `stat_total(stats, KartStatIndex::X)`, and a host fills `stats.base[k]` with wire float k as the 0xC0 record carries it. The enum counted from car+0x3440 until the eleventh pass, two ahead of the wire, so the port ran each formula on the float two places off (the steering gain took wire 4, 0.30, where the recorded kart carries 0.52 on wire 2). `stat_bonus_add_part` adds part float k (the 0x0108 record at 0x78 plus 4 k) to bonus wire k, the first ten scaled by one plus the grade over 50.

The tick composes them through `CarState` in `car_state.h`.
