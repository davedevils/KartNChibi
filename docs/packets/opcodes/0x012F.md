# 0x012F

| Direction | Name | Client fn | Server symbol | Size | System | Status |
|---|---|---|---|---|---|---|
| S2C | RoomInvitePopup | sub_47ED90 | NONE | 4 or var | room invite | PROVEN |
| C2S | RoomInviteBroadcastReq | sub_483B80 | NONE | 0 | room invite | PROVEN |

## C2S RoomInviteBroadcastReq

```
payload none
```

ROOM MASTER ONLY. Also gated on a cooldown flag and on a used versus max invite counter
the server should mirror. After sending, the client starts its own cooldown.

## S2C RoomInvitePopup

```
+0x00  i32  gate   if <= 0 NOTHING ELSE IS READ
+0x04  UTF16LE wstr  inviter_name   -> 0x00F33A1C, 0x40 byte slot
 var   u32           room_id        -> 0x00F33A5C
 var   u32           has_password
 -- only when has_password is non zero --
 var   UTF16LE wstr  password       -> 0x00F33A60
size   4, or 4+2*(n+1)+8 [+2*(pw+1)]
```

VARIABLE READ COUNT, both the gate dword and has_password change how many bytes are read.
The whole handler is SKIPPED when client option 11 is non zero, which is the value C2S
0x0130 reports, so the server can pre filter.

## Our server

C2S 0x012F routes to `case C_RANDOM_INVITE` in `GameServerDispatch.cpp`, room master only.

What the exe proves: `FUN_00483B80` sends a zero byte frame, `FUN_00410420` lets the button
through only when the local player is the master, no modal is open, the box is not already
waiting and the room is not full. The two counters it compares, +0x45c30 and +0x45c2c, are
refilled every frame by `FUN_00409EF0` and `FUN_00409F40` with the occupied and the enabled
member rows, the same pair the room header prints, so there is no invite quota anywhere in the
exe. `FUN_00410640` clears the waiting box after 5000 ms on the local clock alone, no packet
can close it early and none is needed.

What the exe does not prove: whether the released server picked one player, broadcast to many,
or ran a real queue, and whether it delivered with S2C 0x012F or S2C 0x006C. Both open the same
popup object at 0x00F2DB98. The client has no CPU or bot concept for an invite at all, a seated
CPU car is just 0x0032 then 0x0021 and looks exactly like a human joining.

So the server asks a human first and keeps the CPU car as the fallback. It takes the sessions
that carry a character, are not in this room and have not turned invites off, prefers one
standing in the lobby, else one sitting in another room that is still Waiting, and sends it
S2C 0x012F with the inviter name, the room id and the room password. The accept of that popup
fires C2S 0x002F into the room. If nobody is there to ask, a CPU car is seated at once. If
somebody was asked and the room is still alone `kRandomInviteWaitMs` 5000 later, the match tick
seats the CPU car then, so the master never watches an empty seat past its own box.

The recipient side is gated on client option 11. Our server stores that value, see
[0x0130](0x0130.md), and `inviteCandidate` in `server/game/include/util/InviteOption.h` drops
every opted out session before the pick, so a random invite is never spent on a client that
would silently throw the popup away.

Our client, since 2026-09-23: the S2C is read as above and opens the invite popup, and the
whole frame is dropped while the deny invite row of the Game Setting is on, as `sub_47ED90`.
