# 0x0004

| Direction | Name | Client fn | Server symbol | Size | System | Status |
|---|---|---|---|---|---|---|
| S2C | CreateCharacterResult | sub_479230 | CharCreatePackets::createCharacterSuccess | 4, or 104+2*(n+1) | charcreate | PROVEN |
| C2S | CreateCharacterRequest | sub_4805D0 | CharCreateHandler::handleCreateCharacter | 4+2*(n+1) | charcreate | PROVEN |

## C2S CreateCharacterRequest

```
+0x00  u32           driver_key   0xBF catalog entry +0x0C
+0x04  UTF16LE wstr  nickname     4 to 11 wchars
size   4+2*(len+1)
```

Client side gates in order: close all popups, socket alive, key >= 0,
`sub_450060(catalog,key)` non zero else MSG_UNKNOWN_ERROR type 2 DISCONNECT,
wcslen non zero else MSG_NEED_NAME, wcslen > 3 else MSG_INVALID_NICK, then MSG_WAIT,
then def_taboo.txt filter which on a hit SENDS NOTHING. Server must answer or client hangs.

## S2C CreateCharacterResult

```
+0x00  u32           result
 -- result == 0 only --
+0x04  UTF16LE wstr  nickname
 var   blob[0x2C]    character_record
 var   blob[0x38]    kart_record
size   4 on failure, 104+2*(len+1) on success
```

First statement is `sub_4538B0` so the popup always closes.
result 0 success. 1 and 3 MSG_INVALID_NICK type 2. 2 MSG_ALREADY_REGIST type 2.
ANY other value including negatives falls through to MSG_UNKNOWN_ERROR type 2 DISCONNECT.
On a reject the creation popup REOPENS itself with a fresh random driver, never resend 0x0003.
Records must be byte identical to what 0x001B and 0x001C carry.

## Our server

Game server only. `CharCreateHandler::handleCreateCharacter` in
`server/game/src/handlers/CharCreateHandler.cpp`, `case 0x04` of `GameServerDispatch.cpp`,
takes the request after the 0x00A7 auth and the 0x0003 popup. The login server has no 0x04
route, its old `handleCharacterCreate` was dead code and is gone.

On success the 0x0004 result 0 goes out with the nick and the two records, then
`GameServer::sendPlayerData` sends the player phase, 0x07 0x1B 0x1C and the rest, the tail
lists, and closes with the stage ack. A fresh character has `tutorial_completed` 0 so that
ack is [0x0016](0x0016.md), stage 14 the licence, which is where the band 0 rule of
[0x0018](0x0018.md) sends a new account anyway. Our own client opens its licence stage on
that ack.

Since 2026-09-23 (needs the new image): the name check folds the name as the client
`sub_4E15E0` does, the 32 marks dropped and A to Z lowered, and searches every word of
`banned_words` folded the same way, so a mark or a capital cannot slip a word past it, and the
seven single marks of `def_taboo.txt` are in the list (migration 066). A percent sign is
refused, the stock box refuses it and `sub_446280` formats with the name. The driver row gets
its body face and head keys at the insert and both records of the answer are read back from
the rows, so this 0x0004 is byte identical to the 0x1B and 0x1C that follow (the kart record
said durability 100 on mode 3 while the row and 0x1C said permanent). The starter kit follows
the reference burst of a character with only its grant: no gold, the kart, the driver, a
placed sky and floor, and two welcome Gacha Coins 2001 and 2000 in the mailbox from the house.
Tests `NicknameTaboo` in `tests/server/test_pendant_mission_creation.cpp`.

The client side, proven on the package server by `create_driver.txt`: an empty name, a name
under four characters and a taboo word are refused by the client itself with `MSG_NEED_NAME`
or `MSG_INVALID_NICK` and no packet, a taken name comes back as result 2, the OK of the
refusal box opens a fresh popup. There is one character per account, no select and no delete.
