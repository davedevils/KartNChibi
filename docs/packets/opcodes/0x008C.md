# 0x008C

| Direction | Name | Client fn | Server symbol | Size | System | Status |
|---|---|---|---|---|---|---|
| S2C | MissionComplete | sub_47B9E0 | *MissionPackets::missionCompleteWithReward | 20 plus reward | mission | PROVEN |
| C2S | MissionGoalReached | inline sub_43AB00 | *MissionPackets::parseMissionComplete | 4 | mission | PROVEN |

## S2C MissionComplete

```
+0x00  u32  has_reward   0 or 1, anything else consumes only 12 bytes then returns
+0x04  u64  mission_id   8 bytes read, only the low u32 is used
+0x0C  u32  gold_after   -> profile blob +0x4AC
+0x10  u32  exp_after    -> profile blob +0x4A4
 -- only when has_reward == 1 --
+0x14  reward blob, SIZE CHOSEN BY mission_def+0x28 NOT BY THE WIRE
size   20, or 20 plus the blob
```

Reward blob size by mission_def reward_item_type:

```
0 -> blob[0x2C] character   -> 0x01A56BD0
1 -> blob[0x38] kart        -> 0x01A576D8
2 -> blob[0x1C] item        -> 0x01A5A0E8
3 -> blob[0x1C] part        -> 0x01A584E0
4 -> blob[0x1C] pet         -> 0x01A69708
5 -> blob[0x30] roomcraft   -> 0x01A76218, rec+0x08 == 3 updates in place
6 -> blob[0x84] carcraft + u8 hasExtra [+ blob[0x34] extra]
7 -> blob[0x08] { key, count }
```

Writes gold and exp but NOT level and NOT exp_to_next, follow with S2C 0x0A or the XP bar
denominator goes stale.

## C2S MissionGoalReached

```
+0x00  u32  mission_id
size   4
```

Sent the instant the goal is met. Immediately before building it the client reads the
progress row, so a mission missing from the 0x88 list crashes here too.

## Our server

`MissionPackets::missionCompleteWithReward` checks the blob against `rewardBlobSize` before it
sends, so a wrong size is caught. A wrong layout inside the right size is not, and the type 1
kart blob had one: `MissionPackets::kartReward` wrote the durability at +0x08 and a maximum
durability at +0x0C, then seven stats over +0x10 to +0x2C. On the real record +0x08 is the
paint key and +0x0C the name plate key, see [0x00C0](0x00C0.md) for where those keys come from
and `InventoryPackets::kartBlob` for the record our own inventory already shipped correctly.
A zero paint or plate key makes `sub_4510C0` return null and the kart never builds, and the
stats landed on the model builder slots, the two applied items and the period pair.

The C2S side repeats: state 3000 of `0x43AB00` sends 0x008C every frame until the answer
lands. Since 2026-09-23 (needs the new image) `MissionHandler::handleMissionComplete` answers
the first one of a run and drops the repeats (the state row keeps counter minus one), a claim
with no started run gets has_reward 2 (`MissionPackets::missionRefused`, twelve bytes, the
client moves on and marks nothing), the reward item of the def goes out on a first clear:
type 7 the pendant row (instance and key, `MissionPackets::pendantReward`, a row in
`owned_pendant`), types 0 to 6 through `ShopHandler::grantReward` with the record the shop
buy sends, the kart with its paint and plate keys. After the answer the stats refresh 0x000A
and the level banner go out since this packet writes no level. Tests `MissionReward`.

`kartReward` now takes the instance, the base key, the paint, the plate, the kart item key and
the period pair, and writes them at 0x00 0x04 0x08 0x0C 0x10 0x2C 0x30 with the active flag 0
at 0x34, a reward lands unequipped. The durability is period mode 3 with the value at 0x30,
the same rule migration 060 wrote on `owned_kart`.

The same mistake was in `PacketBuilder::kartRecord`, the helper `InventoryPackets::kartBlob`
builds on, harmless there because every dword was rewritten after the call, and in the dead
`PacketBuilder::vehicleInventory`. Both write the real record now.
`PacketBuilder::inventoryVehicles` put the same stat block on 0x001B, which is the driver
inventory with a 0x2C record, and it is gone; `InventoryHandler::sendVehicleList` sends the
0x001C vehicle list instead. `GhostPackets::defaultKartBlock` was already right.
