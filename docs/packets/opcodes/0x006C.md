# 0x006C

| Direction | Name | Client fn | Server symbol | Size | System | Status |
|---|---|---|---|---|---|---|
| S2C | RoomInvite | sub_47B030 | SocialPackets::roomInvite | var | messenger | PROVEN |
| C2S | RoomInviteByName | sub_481CD0 | SocialPackets::parseNameRequest | 2*(n+1) | messenger | PROVEN |

## S2C RoomInvite

```
+0x00  u32           reply_key
+0x04  UTF16LE wstr  inviter_name    dest 26 bytes, cap 12 units plus NUL
 var   ASCII cstr    unknown         dest 34 bytes, NO reader
 var   u32           unknown         NO reader
 var   u32           room_id
 var   UTF16LE wstr  room_password   dest 18 bytes, 8 units plus NUL
 var   u8            flag
size   4+2*(name+1)+strlen(ascii)+1+4+4+2*(pw+1)+1
```

MIXED ENCODING, two UTF16 strings with an ASCII cstr BETWEEN them. Most dangerous layout
in this range. FIELD 2 IS THE INVITER NAME, FIELD 6 IS THE ROOM PASSWORD.
The handler AUTO DECLINES without showing the popup and answers C2S 0x6D:
race or mission stage answer 6, smalltalk modal answer 4, other modals answer 5,
already in that room answer 7.

## C2S RoomInviteByName

```
+0x00  UTF16LE wstr  target_name
size   2*(len+1)
```

## C2S name request family

Shared payload, the block is in [0x006F](0x006F.md).

## Our server

C2S 0x006C by name routes to `SocialHandler::handleNameRequest` then `doRoomInvite`
in `server/game/src/handlers/SocialHandler.cpp`. `SocialHandler::roomInviteRefusal`
(`server/game/include/handlers/SocialHandler.h`) picks the answer and every refusal goes back to
the inviter as a S2C 0x0126 system line, never silence:

| Case | Key on 0x0126 | Text of the stock table |
|---|---|---|
| the inviter is not in a room, the room is gone, or the target is the inviter | `MSG_UNSUPPORT` | Not available. |
| the target is offline, or blocks the inviter (the block is never told) | `MSG_NOT_FIND_USER` | the missing user line |
| the target sits in the same room | `MSG_REJECT_SAME_ROOM` | Player is in same game room |

Else it sends S2C 0x006C with the reply key set to the inviter character id, the inviter name, the
room id and the room password.

The lobby case was dropped with a warning before 2026-09-23. The stock client sends 0x006C from the
lobby too: the Invite item of the messenger row menu is id 0xD of `FUN_00467A70`, whose jump table
at `0x4689E0` goes to `0x46862B` and calls `sub_481CD0` with the friend name, no room check and no
grey state (`FUN_00464A50` opens the six items the same way in every stage, `FUN_00468A00` case 1
draws them all). So the server has to answer. `sub_47EC00` prints the resolved key alone in the
lobby or the room chat, our client does the same since 2026-09-23.

`tests/server/test_race_start_and_invite.cpp` checks every case and reads the 0x0126 bytes back the
way the client parser does. The package image `knc-server:20260919a` still drops the lobby invite,
the fix reaches it with the next image. `tools/client_scripts/invite_lobby_sample.txt` proves the
client side on the sample server, which answers the same way.
