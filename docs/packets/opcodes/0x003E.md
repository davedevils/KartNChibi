# 0x003E

| Direction | Name | Client fn | Server symbol | Size | System | Status |
|---|---|---|---|---|---|---|
| S2C | GridSpawn | sub_479D60 | SpawnPackets::gridSpawn | 176+2*(n+1) | race | PROVEN |

## S2C GridSpawn

```
+0x00  u32           player_id
+0x04  UTF16LE wstr  display_name   the ONLY wide field
 var   u32           start_grid_index
 var   u32           team
 var   blob[0x2C]    character_record
 var   blob[0x38]    kart_record
 var   u32           pet_base_key
 var   blob[0x3C]    custom_car_block
size   176+2*(name+1), packed, no alignment padding
```

READ ORDER 4, wstr, 4, 4, 0x2C, 0x38, 4, 0x3C. One packet per racer INCLUDING the local
player. All reads are unconditional so a bad entry still consumes the right byte count, but
character[+0x04] and kart[+0x04] must resolve or the spawn aborts with MSG_UNKNOWN_ERROR.
The server NEVER sends a world position, only start_grid_index resolved against start.ini.
SLOT RULE: in stage 9 the car slot IS grid_index, in stage 11 the slot is the first free of
30 and grid_index is only the start line index. Must arrive AFTER 0x14.

## Our server, where the two blobs come from

Same records as the room member. `blob[0x2C]` is the record of [0x001B](0x001B.md) and
`blob[0x38]` is the record of [0x001C](0x001C.md), so `character[+0x04]` is
`driver_base_key` into the 0xBF driver catalogue and `kart[+0x04]` is `kart_base_key` into
the 0xC0 kart catalogue. Those are the two keys that must resolve or the spawn aborts with
MSG_UNKNOWN_ERROR.

`RaceHandler::sendGrid` in `server/game/src/handlers/RaceHandler.cpp` calls
`GameServer::loadoutBlobs` in `server/game/src/GameServerLoginBurst.cpp`, which runs the
same `buildRoomMember` the 0x21 uses, or `buildBotMember` for a CPU car. So a racer carries
byte identical blobs in its 0x21 and its 0x3E.
`pet_base_key` is the one field with no source on the room row, we send 0.

`RaceHandler::loadTrackData` builds the row count `sendGrid` hands to
`SpawnPackets::assignGridIndices`. A `track_spawn` table shorter than the seated racer
count, maps 100 and 101 hold one row, used to make `assignGridIndices` drop every racer
past that count with no 0x3E built for them. The loader now widens a short db grid with
the `start.ini` rows of the track folder when that file has more, then pads any remainder
with generated rows stacked on the up axis, so `grid.size()` always reaches the seated
racer count and no racer is silently dropped from the line.

### The pet key, 2026-09-24

`RaceHandler::sendGrid` fills `petBaseKey` with `GachaHandler::equippedPetBaseKey` of the racer,
it was a constant 0, so the other racers now fly their pet through `sub_479D60` and `sub_48CBB0`.

### The custom car block, 2026-09-24

`sub_479D60` hands the 0x3C block to `car_apply_kart_loadout` 0x490A70 as its fifth argument,
15 dwords: +0x00 the chassis kart key, then seven pairs of `0x0108` part key and grade in the
0x20 config order, cover, tires, booster, bumper, front fender, rear fender, wing. When the
`0x00C0` model scheme is 1 the loadout runs `stat_bonus_add_part` on each pair, takes the grip
triple of the tires def (+0xCC), loads `Car/FactoryCar/CHASSIS/<model>` in the texture set of the
mean grade over zero and one nif per pair in the set of its own grade. A plain kart block is all
zero. `CustomCarPackets::customCarBlock` writes it, the client reads it into `Racer::customCar`
and builds the factory kart from it (`kartViewModel` in `client/ui/CharPanel.cpp`).
