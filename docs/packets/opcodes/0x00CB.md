## C2S ConsumableUseNotify

```
+0x00  u32  instance_id     rec+0x00
+0x04  u32  base_key        rec+0x04, always 1000, sub_4516D0 finds the row by it
+0x08  u32  price_key       rec+0x08, the 0xC6 price row key
+0x0C  u32  period_mode     rec+0x0C
+0x10  i32  period_value    rec+0x10, remaining uses, already decremented locally on flag 1
+0x14  u32  active_flag     rec+0x14
+0x18  u32  in_use_flag     rec+0x18
+0x1C  u8   flag            0 screen entry sync, 1 one use just consumed
size   29 exactly
```

The 28 bytes are the owned consumable row of base key 1000 verbatim. sub_4516D0 scans the
0x1D container on rec+0x04 and returns the RECORD BASE, not base minus 4, so the wire starts
at the instance id. The older server struct that read a template id at +0x04 was reading the
base key, its `leaked` dword was the instance id.
No S2C 0x00CB exists. Guards before the flag 1 send: row exists, active flag non zero,
remaining count > 0, then the client decrements rec+0x10 LOCALLY.
The client never waits for an ack. Treat the row as untrusted.

## The Slot Exchange, pass of 2026-09-23

The row is the owned item of base key 1000, `ITEM_1000_TITLE` "Slot Exchange". The race keeps an item
object at 0x2EB4848: held count +0x30BC, the slots `int[3]` at +0x30D8 +0x30DC +0x30E0 (-1 empty). Two
slots are always open (`FUN_004AECD0` and `FUN_004AFF00` refuse a third item unless a row of 5000 is in
use with uses left), the third needs item 5000. A box pickup rolls on the client (`FUN_004B0570`), goes
out on C2S 0x0049 and lands in the next free slot 50 ms later (`FUN_004AEFA0`), then C2S 0x00CF reports
the three slots. The server never fills a slot of the local HUD.

The swap `FUN_004AEDD0` runs on the key of `Input.ini [keyboard] slot`, 18 VK_MENU by default
(`FUN_0045AF60` 0x45AFAE), in the race stages 0xB 0xD 0xF 0x11 0x19, never in a speed mode or under a
rocket lock. It needs the 1000 row, two items held and the 300 ms cooldown free, and pays only when
+0x14 is set and +0x10 is above 0: it lowers +0x10, swaps slot 0 and slot 1, sends C2S 0x00CF with the
new order, then this 0x00CB flag 1 through `sub_482F10` (its only caller 0x4AEEC0). One use per swap,
nothing per race. The flag 0 send `sub_482DB0` is the lobby init 0x4090ED and the waiting room init
0x41143C. The race HUD `FUN_004AFF60` draws the frames `Panel/ItemSlot/slot window.png` at 6 3 and, in
the item modes 0 1 4 with a 1000 row, the `change_01` or `change_02` button with the uses left.

## Our server

`RaceHandler::handleSwapTicket`, since 2026-09-23 (needs the new image): the 29 byte frame with base key
1000 at +0x04 comes here in or out of a room. The owned row must be the instance of the frame.
`util/SlotExchange.h` `slotExchangeStep`: flag 1 on an active row with uses stored takes one use in the
database, and any difference between the stored count and the count of the frame goes back on
[0x0115](0x0115.md). The server no longer swaps its slot model, the 0x00CF before the frame already holds
the new order, the old second swap put the model back to the old order so the next 0x0047 missed slot 0
and a shield swapped to the front was never armed. Test `SlotExchange`.

Docker proof 2026-09-23, stock client on an isolated oracle (the package database copy, the server of this
change), `tools/stock_docker` scenario `slotswap` on `dock1` with a 1000 row of 50 uses: an item single room
race with Alt held every 4 s, the HUD draws the two frames and the swap button counting 50 down to 22, the
items trade places, 28 frames of flag 1 each took one use (`wire 49 stored 50 after 49` down to `wire 22
stored 22`), then the flag 0 syncs of the room and the lobby found `wire 22 stored 22`, the database row
ends at 22, no 0x0115 was needed.
