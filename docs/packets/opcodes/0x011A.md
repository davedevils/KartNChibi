## S2C PendantOwnedAppend (family 0x011A 0x011B)

```
+0x00  u32  pendant_instance_id   sub_4511D0 removes the FIRST row whose +0x00 equals it
+0x04  u32  pendant_key           sub_451290 finds the row by it
size   8, both opcodes
```

The dispatcher folds cases 282 and 283 into ONE handler, the client cannot tell them apart,
so which of the two is the login bulk and which the live grant is a server convention, the
server sends 0x011A at login and reserves 0x011B for a live grant.
Blind append into 0x01A95244, stride 8, cap 64, sub_451140. No dedupe.
The remove path sub_451250 (S2C 0x00A3 case 7 and 0x00F8 case 7 call it before appending
the new row) looks the row up by pendant_key then erases by pendant_instance_id, so the id
MUST be unique per owned row: with every row carrying 0 the first row is erased instead of
the matching one.
The pendant grid only lets you equip a key present in BOTH the 0x0119 list and here.

## Our server

Since 2026-09-23 (needs the new image) each owned row carries its key as the instance id, one
character owns a key once, so the remove of `sub_451250` finds the right row; every row
carried 0 before. The UNION with a `clans` table is gone, there is no guild in this client.
The login also grants the pendants the text table promises and the character already earned:
PENDANT 01 for a licence grade, 06 and 07 for 100 and 1000 races, 08 to 12 for the levels 10
to 50 (`ProgressionHandler::grantEarnedPendants`, `util/PendantRules.h`); a race end and a
level up grant them live on [0x011B](0x011B.md). Tests `PendantRows`, `PendantGrants`.
