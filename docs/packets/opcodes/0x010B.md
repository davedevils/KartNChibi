## C2S CarCraftSaveReq

```
+0x00  u32         preset_id
+0x04  blob[0x20]  car_config { kart_instance, COVER, TIRES, BOOSTER, BUMPER, F_FENDER,
                                R_FENDER, WING }
+0x24  i32         part_count
+0x28  part_count x blob[0x84] part instance
size   0x28+0x84*part_count
```

The client sends its FULL local part list with mutated refcounts, not a delta.
Everything past preset_id is attacker controlled INCLUDING grade at +0x80.

## S2C CarCraftSaveResult

```
+0x00  u32         preset_id
+0x04  u32         slot_state
+0x08  u32         selected_kart_instance_id   -> 0x01A20B1C UNCONDITIONALLY, before any
                                                  lookup, it CHANGES the selected kart
+0x0C  blob[0x20]  car_config
+0x2C  i32         part_count
+0x30  part_count x blob[0x84]   only wire dword 0 and wire dword 3 are consumed
size   0x30+0x84*part_count
```

The 0x84 rows are read and mostly discarded but MUST still be present.
Always ends with MSG_SAVE_DONE, there is NO failure variant, a rejected save must still
send 0x010B with the OLD values.

## Our server

C2S 0x010B routes to `CarCraftHandler::handleSave`. The Save button (sub_42F3E0)
is the only Car Craft verb on the wire, install and remove stay local until it.
The handler checks the preset against `custom_car_preset`, the owned karts and the
owned parts, writes the config, rewrites the `custom_car_part_instance` refcounts
from every preset, and always answers 0x010B with the stored preset and the db
truth part list. A refused save answers 0x010B with the old values then a
MSG_UNSUPPORT box.

Every owned chassis has its own built row since 2026-09-24, so a save edits the parts of that
chassis. `CustomCarPackets::presetIsBuildable` wants an owned kart of a factory template
(`vehicle_templates.is_factory_car`, the only karts the chassis tab lists) that no other built
row holds, and an owned live tire, as `sub_42F3E0` does before it sends. The chassis tab can put
another owned chassis on a row, that chassis already has its row so the save answers the stored
row then MSG_UNSUPPORT. The answer keeps the name, 9 chars at most. The equip counts of the reply
are the built rows holding each part. `sub_47E530` selects the answer kart with no test, the
handler writes it to `characters.selected_kart_instance_id` so the garage In Use and the next
login agree with the client.

Kart ownership and the chassis catalog key read `owned_kart`, the id the wire
actually carries. The legacy `vehicles` table only ever got a row for the starter
kart, a shop or gacha kart never landed there, so a save on any later kart used to
find no owner and fall back to the stored preset with a wrongly forced
MSG_UNSUPPORT. Migration 064 dropped that table and every reader is on `owned_kart`
now, so the car craft sees every kart the character owns.
