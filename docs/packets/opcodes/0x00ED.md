## S2C GachaResult

```
+0x00  blob[0x14]  header, five dwords. header dword 1, wire +0x04, IS THE CATEGORY SWITCH
+0x14  blob[0x1C]  updated ticket row, matched by its +0x04 against the 0x001D container
+0x30  typed prize tail chosen by the category
size   92 cat0, 104 cat1, 76 cat2, 76 cat3, 96 cat4, 181 or 233 cat5, 48 cat6 and up
```

```
0 -> blob[0x2C] owned character
1 -> blob[0x38] owned kart
2 -> blob[0x1C] owned item
3 -> blob[0x1C] owned part
4 -> blob[0x30] roomcraft, stackable when row+0x08 == 3, count at row+0x28
5 -> blob[0x84] carcraft FIRST, THEN u8 has_slot, THEN blob[0x34] when has_slot == 1
6 and above -> nothing read
```

`CMP EAX,0x5 / JA` at 0x0047d64a proves category >= 6 reads nothing.
TAIL BYTE ORDER: 0x00ED cat 5 and 0x0135 cat 6 read the blob FIRST then the u8.
0x00B7 cat 6 reads the u8 FIRST. Do not share one serializer.
The ticket decrement MUST be reflected in the echoed row, the client never decrements.

## C2S GachaRoll

```
+0x00  blob[0x1C]  verbatim copy of the owned ticket row, base key 2000
size   28
```

Send guards: row exists under base key 2000, active flag non zero, remaining > 0.
The PLAY button is dead otherwise, so there is no client path for an insufficient reply.

## Our server

C2S 0x00ED routes to `GachaHandler::handleRoll`. The gacha popup init sub_4576B0
sends nothing, the Play button (sub_4830C0) sends 0x00ED. The handler loads the
ticket from `owned_item` on base key 2000, rolls the weighted `gacha_items` pool,
grants the prize in one transaction, decrements the ticket, and answers 0x00ED with
the echoed decremented ticket and the typed prize tail. An empty pool or a failure
answers 0x00ED category 6 with the unchanged ticket, the only clean refusal since
there is no gacha reject opcode.

### The Gold Coin tab is live, 2026-09-23

The popup has two tabs, `Gacha_tab_C` "ASTRO Crazy Lotto" and `Gacha_tab_P` "GOLD Crazy Lotto". The mouse
handler `FUN_00456830` writes the tab index at +0x1AA44 (0x456904), the frame `FUN_004571D0` looks up the owned
row of base key 2000 for tab 0 and 0x7D1 (2001) for tab 1 and Play sends that row. The old note that called the
2001 tab dead was wrong, `GachaPetPackets::GOLD_COIN_BASE_KEY` replaces the unused name and the warning went.
A coin must be a mode 2 row with a count, so a buy of 2000 or 2001 now adds one coin whatever unit the price
row prints (the burst sells both on unit 0 rows). Live on the package, 2026-09-23: the Gold Coin bought for
3000 gold on our old row, the gold tab START sent this frame with instance 10 key 2001 count 5, the answer was
category 0 driver 12 with the row at count 4. Tests `ShopCoinGrant.*` in `tests/server/test_shop_catalogue.cpp`.
