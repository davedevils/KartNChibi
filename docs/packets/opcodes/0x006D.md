# 0x006D

| Direction | Name | Client fn | Server symbol | Size | System | Status |
|---|---|---|---|---|---|---|
| S2C | ignored | nullsub_1 | NONE | 0 | no op | NULLSUB |
| C2S | RoomInviteAnswer | sub_481D70 | *SocialPackets::parseRoomInviteAnswer | 8 | messenger | PROVEN |

## C2S RoomInviteAnswer

```
+0x00  u32  reply_key     the u32 from S2C 0x6C
+0x04  u32  answer_code
size   8
```

Codes proven at their call sites: 1 user declined, 4 busy in a smalltalk modal,
5 another modal is up, 6 in a race or mission stage, 7 already in that room.
ACCEPT DOES NOT USE THIS OPCODE, accept sends C2S 0x2F with the room id and password.
The S2C side of 0x6D is a nullsub, never answer with an echo.

## Our server

C2S 0x006D routes to `SocialHandler::handleRoomInviteAnswer`. The reply key is the
inviter id the server chose in the 0x006C, so it finds that session and shows it the
reject line for the answer code. Accept never uses 0x006D, the client sends 0x002F
with the room id and the password. The S2C side of 0x006D is a nullsub, never echoed.
