## Our server

One builder for every way into a room. `GameServer::sendRoomScreen` in
`server/game/src/GameServerRaceHandlers.cpp` sends this frame first, then the thirty
[0x0032](0x0032.md) slots, one [0x0021](0x0021.md) per member with the receiver last and
the CPU cars after it, then [0x0030](0x0030.md) with the room master and
[0x0035](0x0035.md) with the room track, all in one write. The callers are the 0x2D create,
the 0x2F join, the 0x2C and lobby 0x64 quick match, and the room screen resend once the
result board is done. A joiner also fans out to the peers through
`GameServer::announceRoomJoin`, 0x32 then 0x21 for its slot.

The fields are `PacketBuilder::playerRoomData` in `server/game/src/packets/PacketBuilder.cpp`
then `RoomCraftHandler::appendRoomDecor` for the count and the records:

```
room_id            room id
room_name          the room name
max_players        settings max
game_mode          settings mode 0..4
has_password       0
unused_2           the track id of the room, the 0xC3 id the 0x35 carries, never the map id
unused_3           0
unused_4           0
master_player_id   Room::hostCharacterId, the real master, never the receiver
weather            0
object_count       the placed Room Craft rows of the master, or the safe decor of the room
```

`unused_2` used to carry `track_catalog.map_id`. The stock client has no reader for that
dword, the only reference to `0xBCE214` in the image is the store at `0x0047FC7D` inside
`sub_47FC20` itself, so the value is free. It now carries the track id because the map id
is a server side space the client never speaks, see PROTOCOL.md, track ids and map ids.
