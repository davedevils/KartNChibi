# 0x00A7

| Direction | Name | Client fn | Server symbol | Size | System | Status |
|---|---|---|---|---|---|---|
| S2C | ReauthAccept | sub_479080 | CharCreatePackets::reauthAccept | 1228 | session | PROVEN |
| C2S | Reauth | sub_480500 | GameServer::handleSessionConfirm | 12+2*(n+1) | session | PROVEN |

## S2C ReauthAccept

```
+0x00  u32         player_id
+0x04  blob[0x4C8] profile
size   1228
```

Byte identical twin of S2C 0x0007 MINUS the launcher `FindWindowA` notification.
The blob ends exactly where the 0xBF driver catalog container starts, an oversized blob
overwrites the catalog.

## C2S Reauth

```
+0x00  ASCII cstr    client_version   literal "178"
+0x04  u32           target_stage     the mode carried by S2C 0x0019
+0x08  UTF16LE wstr  reauth_token
 var   u32           reauth_session_id
size   12+2*(len+1)
```

MIXED ENCODING and a DIFFERENT argument order from 0x0007.
This is what the client actually sends on every connection after the first successful
login of the process. The two fields are the head of the S2C 0x0007 blob echoed back,
our login server writes the account id at +0x000 and a 32 char token at +0x004 there
and the game server binds the socket on the pair, see PROFILE_BLOB.md.

## Our server

`CharCreatePackets::profileBlob` in `server/game/src/packets/gen/CharCreatePackets.cpp`
builds the 1228 bytes for both `loginAccept` 0x0007 and `reauthAccept` 0x00A7, so the two
really are byte identical twins on our wire. `CharCreateHandler::sendReauthAccept` sends it
and logs an error if the payload is not exactly `PROFILE_BLOB_SIZE`, 1228.

The blob follows THIS PAGE. Careful when reading that function, it writes the player id at
its own +0x000, so every literal offset in it is 4 higher than the blob relative offsets
used here:

```
function +0x4A4 band          =  blob +0x4A0
function +0x4A5 level         =  blob +0x4A1
function +0x4A8 expCurrent    =  blob +0x4A4
function +0x4AC astro         =  blob +0x4A8
function +0x4B0 gold          =  blob +0x4AC
function +0x4B4 selChar       =  blob +0x4B0
function +0x4B8 selKart       =  blob +0x4B4
function +0x4C0 expFloor      =  blob +0x4BC
function +0x4C4 expNext       =  blob +0x4C0
function +0x4C8 titleKey      =  blob +0x4C4
```

Our LOGIN server does not follow this page, it puts gold at blob +0x4A4 and cash at
blob +0x4AC. See [0x0007](0x0007.md) and CONFLICTS C1 in `../PACKET_REGISTRY.md`.

### The channel return on the login server

`HandshakeHandler::handleReauth` in `server/login/src/handlers/HandshakeHandler.cpp` answers
C2S 0x00A7 on the login socket. It lands on a brand new socket with no 0x00FA in front, so no
handshake state is required. The payload order is the one `sub_480500` writes: the ascii
version, the u32 stage, the wide token of blob +0x004 and the u32 account of blob +0x000.

The ticket cannot come from `active_sessions`, the game server deletes every row of the
account when it binds the redirect on its own 0x00A7. Migration 063 adds `login_ticket`, one
row per account, written by `sendSessionInfo` at the same moment it writes the blob head.
`handleReauth` matches the account and token pair against that table inside one day, then
answers S2C 0x00A7 with the same 1228 bytes 0x0007 carries, then the empty 0x0002 and then the
0x000E channel list. The 0x000E is what runs `FUN_00404410(4)` and opens the channel screen,
the 0x00A7 only refreshes the client profile global. The duplicate login guard is skipped here
on purpose, the account is coming back from its own game socket.

An unknown or expired ticket answers MSG_REINPUT_IDPASS with code 2 and closes after the send,
so the client falls back to typing the credentials instead of hanging on MSG_WAIT.

The blob 0x4C4 is the worn pendant 0x01A20B2C that `sub_479080` copies, since 2026-09-23
`writePlayerInfo` puts `characters.pendant_key` there instead of the rank points.
