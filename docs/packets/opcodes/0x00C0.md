into the container 0x01A22638 (this+0x810188 of the net object), cap 64, stride 0x140, count at
container+0x5004. Lookups: `kart_catalog_lookup` 0x44F6F0 by key at rec+0x08, `kart_catalog_by_index`

ALL THREE STRINGS ARE ASCII. WIRE ORDER IS NOT RECORD ORDER, the two ability pairs are read
BEFORE the count but live AFTER the inline price list object (0x48 bytes at rec+0xE8) in the record.
Send only after 0x00BE, the container is pure append with no upsert. The vehicle_kind is 2 on every
chibikart kart row.

### The 17 stats, rec+0xA4 + 4*k, WIRE index k

Settled on the bytes 2026-09-15 (docs/reverse/physics/INPUT_AND_STATS.md "The 17 stats, wire
numbering, settled"). `car_apply_kart_loadout` 0x490A70 copies the record from byte 0 to car+0x33A4
(`LEA EDI,[EBP+0x33A4]; MOV ECX,0x50; MOVSD.REP` at 0x490AF0), so rec+0xA4 lands at car+0x3448 and
wire float k is car+0x3448 + 4k, its part bonus car+0xA7940 + 4k (`stat_bonus_add_part` 0x48F710
adds the 0x0108 part record 0x78 + 4k there). car+0x3440 and car+0x3444 are rec+0x9C and rec+0xA0,
the skin keys 6 and 7, not stats. An older numbering counted from car+0x3440 and sat two ahead of the
wire, migration 057 carried it into the column names, migration 059 renames them to this table.
The garage bars come from `garage_stat_bars_compute` 0x428AB0, each bar a min max normalise over the
whole catalogue: bar one Speed wire 0 + 1, bar two Handling wire 2, bar three Drift wire 8 + 10 + 11,
bar four Booster wire 3.

The part bonuses added on top come from the 0x0108 CarCraftPartDefinition record at +0x78, NOT from
0x00C2: `stat_bonus_add_part` 0x48F710 looks the part up with `part_def_record_lookup` 0x44FBC0 in the
0x120 stride container and adds its 17 floats by the same wire index, the first ten (wire 0 to 9)
scaled by 1 + grade div 50 where grade is the second dword of each 0x3E loadout pair, the last
seven flat. The 0x00C2 record has no stat block. The camera three take no bonus, `camera_update`
reads the base copy only.

### Ability pairs

`kart_ability_pairs_draw` 0x42B910 walks the two pairs at rec+0x130 and rec+0x138 and draws an icon
plus `sprintf("%d%%", percent)` for every pair whose id passes `-1 < id && id < 0x1a`, a SIGNED
compare. So id 0 percent 0 is a real ability drawn as "0%", not an empty pair. The hiding value is any
id outside 0 to 25 and the released server used -1: every one of the 46 kart rows of
`server/data/reference_login_burst.bin` carries `FF FF FF FF 00 00 00 00` twice, and so do all 473
part rows (`part_ability_pairs_draw` 0x42B1B0 is the same loop on rec+0x84). No kart on the real
wire has an ability. `catalogue_ability_check` 0x4B8460 compares a race ability id with the pair id,
-1 never matches. Our server sent 0 0 until 2026-09-15 which drew two "0%" icons on every kart tile.
`writeKartDefinitionBody` now takes `KartAbilityPair` with id `KART_ABILITY_NONE` (-1) as the default,
`PacketBuilder::vehicleCatalog` passes it through and no catalogue column exists because the burst
gives nothing to seed, a kart with a real pair goes in through the optional last argument.

### Durability and repair

There is no durability or repair field in this packet or in any catalogue. The kart durability is
the owned kart record (0x38 stride, `owned_kart_lookup` 0x44F450 by instance id): +0x28 price key,
+0x2C period mode, +0x30 period value, +0x34 active. With period mode 3 the value is the durability,
0 to 500 (`kart_durability_bar_draw` 0x42AD20 clamps at 500 and draws the empty bar under 2),
`race_return_durability_warn` 0x4795A0 shows MSG_DURABILITY_ZERO under 1 and MSG_DURABILITY_LOW
under 11 when the race stage returns. The repair verb: `shop_buy_click` 0x412BC0 takes a 0x00C1 row
with use_type 4 to 7 on a kart whose period mode is 3 and opens MSG_REPAIR_USE, the scroll costs its
own price row (0x00C6 through its price option). The amount restored and the loss per race are
server side, the client only displays +0x30. The "car+0x9C4 family" of an older note does not exist,
no instruction in the image reads [reg+0x9C4] and 0x48D730 is `car_wheels_in_air_count`. A price row
with unit type 3 and unit amount N sells N durability, that is the only rate on the wire.

What the real burst shows: no kart is sold with period mode 3. All 46 kart rows carry the same three
price options `(2002, mode 1, 1 day)`, `(3002, mode 1, 7 days)`, `(1002, mode 0, permanent)`, the 23
0x00C6 rows have unit types 0, 1 and 2 only, the owned kart 10035 of the capture is period mode 0,
and the two 0x00C1 rows are the gacha coins with use type 0. Durability on the released wire is a
client feature the server never fed, so every number below is the emulator rule.

The repair verb on the wire: 0x412BC0 is the garage install click (it is the caller of the 0x00B9
sender 0x4842F0, the name shop_buy_click is historical). On the item tab it looks the tile key up
in the 0x00C1 catalogue, use type 4 to 7 on a selected kart with period mode 3 opens MSG_REPAIR_USE
and the yes callback FUN_00461230 sends C2S 0x00B9 category 2 with the item key. The ack is 0x00B9
category 2 with the item record plus the 16 byte kart period block, 0x484770 copies that block over
the selected kart, see [0x00B9](0x00B9.md). There is no other repair path in the exe, no function
named repair, no garage button, no gold repair.

### Default skins of a factory kart, 2026-09-23

Every burst kart row, factory chassis included, names the stock paint and plate in the skin slots +0x84 +0x88
(1000 PURPPLE and 1100 NAMEBOX_NORMAL) and -1 in +0x8C. Our factory rows named one 0x0108 part key per slot, which
only resolved through the 0x00C2 twin rows. The factory branch of `car_apply_kart_loadout` reads skin slot 2 only
(the antenna, guarded) and takes the parts from the preset loadout, so our factory rows now carry 9007 and 9100 like
every other kart and the twins are gone, see [0x0108](0x0108.md). The kart tier of the burst is 2002 3002 1002,
migration 068 moves ours there from 2001 3001 1001. Needs the new image.
