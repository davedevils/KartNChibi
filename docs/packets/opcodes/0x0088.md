## S2C MissionProgressList, FULL REPLACE

```
+0x00  i32  count   SIGNED, 0 is legal
 then  count x { u32 mission_id, u32 cleared }
size   4+8*count
```

Container 0x01A4C320, cap 20, count at 0x01A4C3C4. Clears first so a resend is safe.
Sorted ascending by mission_id after every insert, wire order does not matter.
HARD REQUIREMENT: every mission the player can complete MUST have a row here.
Both S2C 0x8C and the C2S 0x8C build path write `*(lookup(id)+4) = 1` with NO null check,
a missing row writes to address 0x00000004 and crashes the client.

## Our server

`MissionPackets::loadMissionProgress` reads every `mission_def` row with its cleared flag and
`MissionPackets::chainProgress` cuts the list after the first row not cleared: the cleared rows in id
order, then the one open row. The slots past the list draw `Mission_lock` (`FUN_0043B7A0`, a slot with
no row takes the lock branch). Before 2026-09-23 every row went out, so a row cleared out of order (the
package `admin` has 0 and 2 cleared, 1 not) drew `Mission_lock` and `Mission_clear` on the same medal
next to a NEW row, the "different states" the user saw. With the chain that row waits hidden until the
row before it is cleared, then [0x008A](0x008A.md) appends it. [0x0090](0x0090.md) refuses a start the
lock rule refuses on the same chain, `MissionPackets::missionPlayable`, tests `MissionLock` and
`MissionChain`. Needs the new image.

Docker proof 2026-09-23 (scenario `videocheck`, `dock1` with missions 0 and 2 cleared like the
package `admin`): the package image draws Lv 1 Clear, Lv 2 NEW, Lv 3 lock plus Clear with Start and a zero
reward, the server of this change draws Lv 1 Clear, Lv 2 NEW and Lv 3 to 5 locked, a click on Lv 3 picks
nothing.
