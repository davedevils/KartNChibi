## S2C PetDefinition

```
+0x00  u32         visible_flag         -> rec+0x00
+0x04  u32         badge                -> rec+0x04, 1 hot 2 new corner sprite
+0x08  u32         pet_key              -> rec+0x08  LOOKUP KEY
+0x0C  u32         required_pendant_key -> rec+0x0C, sub_460A10 at 0x460D53 refuses the buy with MSG_NOT_CONDITION unless sub_451290 finds it in the 0x011A owned pendant list, 0 skips the check
+0x10  ASCII cstr  model_folder         -> rec+0x10, 33 byte slot
 var   ASCII cstr  name_loc_key         -> rec+0x31, 33 byte slot
 var   ASCII cstr  desc_loc_key         -> rec+0x52, 34 byte slot
 var   i32         price_count
 then  price_count x blob[0x10] price row
size   16+3 cstr lengths+4+16*price_count
```

BLIND APPEND into 0x01A67F80, stride 0xBC, HARD CAP 32.
Price vector keeps only the FIRST 4 rows. Cleared by S2C 0x00BE.
All three strings ASCII with an unbounded qmemcpy, longer than 32/32/33 smashes the frame.
The server column is shop_definition.required_pendant_key, the pet_condition table is only a
fallback, the client truth is the owned pendant list.

## Our server

`GachaHandler` publishes one row per `pets` row through `GachaPetPackets::petCatalog`, and the
options come from `shop_option` category 4. The recording sells four pets, keys 5001 to 5004,
each with the tier 2005 one day, 3005 seven days, 1005 permanent. Ours keeps the keys 10 20 30
40 because `petKeyHasRaceEffect` and every `owned_pet` row speak those, and it offers a fourth
three day step 5005 the recording never had. `shop_definition` category 4 carries all four, so
a pet buy passes `ShopPackets::validatePurchase`, unlike the driver accessories before
migration 062.
