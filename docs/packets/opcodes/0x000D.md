# 0x000D

| Direction | Name | Client fn | Server symbol | Size | System | Status |
|---|---|---|---|---|---|---|
| S2C | RankBoardRebuild | sub_47ADE0 | SpawnPackets::rankBoardRebuild | 0 | race | PROVEN |
| C2S | RaceSceneLoaded | sub_4807A0 | RaceHandler::handleSceneLoaded | 0 | race | PROVEN |

## S2C RankBoardRebuild

```
payload none
```

Unrolls the 30 car slots, reads grid_index at car+2508, writes board[grid_index].
SKIPS any index below 0 or 16 and up. grid_index MUST be 0..15 and unique per racer.
Send once, after the last 0x3E.

The handler also writes 1 to `0xB23150`, the stage flag `stage+0x168A8` of the game stage object
at `0xB0C8A8` (`mov dword [0xB23150], 1` at `0x47ADE5`). That flag is what the C2S answer below
waits on.

## C2S RaceSceneLoaded

```
payload none
```

The stock sends it online. The old reading "dead online" was wrong: it only looked for writes
through `[esi+0x168A8]` and found the offline bot branch of `FUN_004028C0` (`0x4030D8`), but the
S2C handler above writes the same flag through its absolute address.

How the stock answers:

1. S2C 0x14 lands, `FUN_00479CC0` closes the popups (`FUN_004538B0`) and calls the stage switch
   `FUN_00404410(0xB)` inside the packet handler. The switch runs the game stage init
   `FUN_004028C0` synchronously: track, items, effects, panel, drivers, cars. No frame is drawn and
   no packet is read while it runs, the window keeps the last room frame.
2. The frames that came meanwhile (0x3E rows, S2C 0x0D) are read after the init returns. S2C 0x0D
   sets `0xB23150` to 1.
3. The next draw of the game stage `FUN_00402210` sees the flag at 1, sets it to 2, sends C2S 0x0D
   through `FUN_004807A0` and starts the track music `FUN_00401BF0`.
4. Every S2C 0x0D sets the flag again, so the stock answers each one. Two S2C 0x0D (the grid one
   and the one before the GO) give two C2S 0x0D, which is the count of the chibikart capture in
   `../RACE_TIMELINE.md`.
5. The stage then waits for S2C 0x3A with the `Panel/Message/WaitPlayer.png` plate, the countdown
   starts when the GO is read.

The stock under wine in `tools/stock_docker` (account dock1, character 25) answered 2870 ms and
760 ms after the grid on the package server of 2026-09-23 (`docker logs knc-game`, rooms 16 and 17).

## Our server

C2S 0x0D is the scene loaded answer and the GO waits on it. `RaceHandler::sendGridPhase` in
`server/game/src/handlers/RaceHandler.cpp` sends the grid, then arms a `SceneLoadWait`
(`server/game/include/handlers/RaceHandler.h`) with every human racer of the room, bots owe
nothing. `RaceHandler::handleSceneLoaded`, routed from case 0x0D in
`server/game/src/GameServerDispatch.cpp`, clears the sender and calls `goRace` once nobody owes
an answer, the log line gives the ms since the grid. A racer who leaves the room between the grid
and the GO is cleared too (`RaceHandler::handlePlayerLeave`), so the others go at once.

The cap is `SceneLoadWait::kWaitMs`, 30000 ms after the grid, then the fallback timer starts the
race with the late racers and logs how many. It was 3000 ms before 2026-09-23: the gate races of
that day started without our client, whose load took 27 s, and the stock under wine answered as
late as 2870 ms. 30 s covers the stock under wine (8 to 16 s load) and the old client.
`RaceHandler::goRace` then runs `startRace`, which sends the S2C 0x0D rank rebuild and the S2C
0x3A GO through `RaceHandler::sendRaceStart`.

The stock answers the second S2C 0x0D a frame after the first one, inside the 50 ms default floor
of the rate limiter, so `makeRateLimiterConfig` in `server/game/src/GameServerBootstrap.cpp` gives
0x0D no floor. The late answer lands after the GO and `handleSceneLoaded` ignores it.

`tests/server/test_race_start_and_invite.cpp` checks the wait: every human owed, a repeated answer
harmless, a leaver cleared, no human no wait, the cap over every measured load. The package image
`knc-server:20260919a` still has the 3 s window, the fix reaches it with the next image.

Our client answers the same way as the stock, `RaceSession::sendSceneLoaded` once per S2C 0x0D,
and only once its track load is done: the race screen holds every frame that comes while the load
runs and replays them in order after it (docs/client/README.md, the race).
