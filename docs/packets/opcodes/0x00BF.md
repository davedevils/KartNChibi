## S2C DriverCatalogEntry

Handler `driver_catalog_recv_0xbf` 0x47F390, store `driver_catalog_store` 0x44FED0 into the
container 0x01A20B30, cap 32, stride 0xD8, count at container+0x1B04. Lookups `driver_catalog_lookup`
0x450060 by key at rec+0x0C, `driver_catalog_by_index` 0x44FF10, `driver_catalog_count` 0x44FFC0.

```
+0x00  u32         visible_flag       -> rec+0x00, shop_tile_draw_drivers 0x419480 skips zero, the creation popup needs it with +0x04
+0x04  u32         creation_pick      -> rec+0x04, FUN_00473730 random pick and FUN_00473860 click take only rows with +0x00 and +0x04 non zero
+0x08  u32         badge              -> rec+0x08, shop_tile_draw_drivers piVar3[2], 1 or 2 draws one of the two tile overlays new and hot
+0x0C  u32         driver_base_key    -> rec+0x0C  LOOKUP KEY
+0x10  u32         required_level     -> rec+0x10, shop_tile_draw_drivers 0x419604 compares with the player level byte 0x1A20B09, shop_buy_button_gate 0x413950 piVar4[4]
+0x14  ASCII cstr  model_asset_name   dest 36 bytes -> rec+0x14
 var   blob[0x14]  default_costume_keys  5 x u32 -> rec+0x38, FUN_0047DD10 copies them into the creation blob, the owned driver +0x08 to +0x18 they become are compared with 0x00C2 rows per equip_slot 2 to 6
 var   ASCII cstr  display_name_key   dest 33 bytes -> rec+0x4C, def_trans key, shop_detail_panel_draw 0x45E3D0 and garage_detail_draw 0x415FF0
 var   ASCII cstr  description_key    dest 35 bytes -> rec+0x6D, def_trans key, the description block
 var   u32         price_option_count read into a local, the rows land in the inline list object at rec+0x90
 then  price_option_count x blob[0x10] -> rec+0x90 rows, cap 4, the list count lands at rec+0xD4
size   45+3 cstr lengths+16*price_option_count
```

ONE entry per packet. All three strings are RAW NUL TERMINATED ASCII, not utf16 and not
length prefixed. Both visible_flag and creation_pick must be non zero or the entry is skipped by the
creation gates. chibikart sends both as zero, which is why their in game creation never worked: the
popup draws empty boxes and its OK handler FUN_00473950 answers MSG_UNKNOWN_ERROR on rec+0x00 being
zero before it ever sends 0x0004. Ours sends 1 and 1 since 2026-09-11.
The price list is a FIXED inline 4 slot object, extras are consumed then dropped, but
price_option_count must exactly match the bytes written or the reader throws Invalid Read.
Observed driver keys 10 20 30 40 50 60 70 80.
`rec+0x14` feeds `Driver/Body/High/%s/body`, `parts/driver_%s_%02d.png`, `Driver/Facial/%s/%s.dds`,
`Image/Panel/Minimap/%s_B` and `Panel/QuestDialogue/Quest_Wanted_%s.png`.
THIS PACKET IS THE HARD PRECONDITION FOR S2C 0x0003.

## Our server, the race roster row

The race start reuses this opcode with the SAME wire grammar and different meanings.
`PacketBuilder::racePlayer1` in `server/game/src/packets/PacketBuilder.cpp` writes:

```
+0x00  u32         player_id          the racer character id
+0x04  u32         kart_base_key      vehicleTemplateId of that racer
+0x08  u32         driver_base_key    driverId of that racer
+0x0C  u32         slot               the room slot, this is the lookup key at rec+0x0C
+0x10  u32         zero               always 0, no field behind it
+0x14  ASCII cstr  display_name       the racer name, low byte of each wchar
 var   blob[0x14]  loadout            kart key at +0x00, driver key at +0x04, slot at +0x08, tail zero
 var   ASCII cstr  display_name       the same name a second time
 var   ASCII cstr  empty              one NUL
 var   u32         row_count          always 0, so no trailing rows
size   45+2*(name+1)
```

`RaceHandler::handleStartRace` in `server/game/src/handlers/RaceHandler.cpp` broadcasts one
row per human session, then one row per bot, before the track catalogue and the grid.
Bots take the same shape so the client cannot tell them from humans.

WHAT TELLS THE TWO LAYOUTS APART is the stage, not the bytes. The reader `sub_47F390` is the
same one and the grammar matches field for field, 5 dwords, one cstr, one blob of 0x14, two
cstr, one count, then that many rows of 0x10. Catalogue rows go out during the login burst
while the client sits in the menu stages, race roster rows go out only from
`handleStartRace` once the room is starting. A roster row that lands at login would be
stored as a driver catalogue entry with `visible_flag` equal to the player id, so never mix
the two phases.

Our roster rows land in the same container as the catalogue rows, so they take container
slots. The cap is 32 entries and the key read at rec+0x0C is the room slot here and a
driver key at login.
