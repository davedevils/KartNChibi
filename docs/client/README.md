# Client

Our own client for Kart N'Chibi on the new stack, glfw and bgfx. Phase 1 is the way in: the window, the JSON screens drawn from the pak images, login on the real server, the channel list, the redirect, the lobby with its real room list. Phase 2 is the room and the race: create or join a room, the track pick, ready and start, the track scene under a race HUD, the local kart on the 1:1 physics port, the other karts on `0x0040`, items, laps, the finish and the result board. Phase 3a is the garage and the shop: the owned lists, the select and equip verbs, the stat and durability bars, a 3D preview of the kart with its driver, the catalogue tabs with the price rows, the detail panel on the shipped text table, the buy verb and the wallet after it. Phase 3b is the rest of the lobby: character creation on a fresh account, the mission menu and a solo mission run, the messenger with the friends and the notes, the whisper, the room password, the teams, sound on miniaudio, and a race between two humans. The server is the reference, the client adapts to it.

The plan with the bricks, the phases and the rules is [`CLIENT_REWRITE_PLAN.md`](CLIENT_REWRITE_PLAN.md).

Namespace `KnC::Client`, C++20.

## Build

```
cmake --preset vs2022
cmake --build build --config Release --target knc_client
```

The exe lands in `release/knc_client.exe`. The target needs `KnCRender` (so `shaderc` must be built, see `engine/render/CMakeLists.txt`) and `glfw`, otherwise the client is skipped and only `client/net` is configured. It links `KnCTrackScene`, `KnCGhostReplay` and `KnCKartClient` for the track scene, the ghost car and the physics port. Reconfigure after adding a file, the target lists its sources.

The headless builds the same library from its own project:

```
cmake -S tools/headless -B build-headless -A x64
cmake --build build-headless --config Release
```

## Start up

The way in is the stock one: the two logo plates, the intro of the title stage, then the login box. The client prints one `[time]` line per start up step and one per screen, so a run tells where its seconds went.

| Step | What it does | Warm | First start with no index |
|---|---|---|---|
| window | glfw window and the callbacks | 80 ms | 80 ms |
| renderer | the bgfx boot of `KnCRender` | 210 to 260 ms | 240 ms |
| font atlas | Arial and Arial bold baked with stb truetype | 13 ms | 13 ms |
| pak open | the pak index read from its cache | 25 to 35 ms | 3 ms, the scan runs on its own thread |
| text table | `def_trans_index` and `def_trans_message` | 2 ms | 2 ms |
| sound engine | the miniaudio device, no clip is decoded yet | 0 ms | 0 ms |
| logo enter | one png, `Logo/OGP_ci.png` | 16 ms | 400 ms |
| login enter | the login art and the four buttons | 110 to 155 ms | 112 ms |

The numbers of 2026-09-18 on the package client folder, `--stop-at login --mute --no-focus`:

| Mark | Before | After |
|---|---|---|
| logo on screen | 3057 ms warm, 24439 ms with a cold file cache | 348 to 700 ms warm, 743 ms with no index yet |
| login on screen | 3491 ms | 1242 to 1605 ms |
| launch to the lobby, `hltest` on the package server | 5280 ms | 3135 to 3667 ms |
| the login press to the lobby | 1727 ms | 1668 to 1759 ms |

The spread of the after column is the build machine, four other agents were compiling during the runs. Every number is a `[time]` line of the client log.

What made the difference:

- `AssetStore` no longer byte scans the 867 MB pak at every start. The scan ran 2.3 s with a warm file cache and 23.6 s with a cold one. The table is written once to `%TEMP%/knc_client/pak_index/pak001_<size>_<time>.txt`, one line per entry with its offset, its size and its path, and read back in 25 ms. A pak of another size or date gets its own file, so a changed pak is scanned again.
- The first start with no cache scans on a thread. Until the table lands every read tries the `Data` folder first, so the logo the intro and the login come off the disk and the window opens at the usual time.
- The image list of the name search is built on the first miss, not at the open, and it walks the folders by string rather than through `std::filesystem::relative`, 44 ms instead of 2032 ms.
- The logo screen loads its one plate, not the menu art of `ui_state_01_logo.json`.
- The sound bank opens its device at the start and decodes a wav only when it is first played.
- While the logo, the intro and the login are up, `App::warmAssets` loads one menu frame image per frame, the wallpaper, `Common_back`, the top and bottom bar buttons and the lobby back. The lobby entry fell from 618 ms to 99 ms.

The race has its own load steps, see Race entry below. The stock shows no loading screen on this path: `Data/<lang>/Image/Title/UI_loading.png` ships with the client but no string in the exe names it, and the stage list has no loading stage between the title and the login. The stock covers the wait with the intro instead, and so do we.

## Race entry

The `0x0014` launch opens the race screen at once and the track loads on a thread, the window keeps drawing. `RaceScreen::enter` takes about 1 ms, the load thread reads the track, the COL, the ini rows and the minimap (`loadRaceWorld`), then decodes every texture of the scene on the spare cores (`KnC::Render::prefetch_textures`), then hands over. The main thread does the rest in `RaceScreen::finishWorld`: the sim, the device upload (the GPU textures only, the files are read already), the weather, the gauge, the countdown nif, the gimmick rows. The car effect nifs parse on the same thread after that and join the race when done (`RaceEffects::parseAll`, `adopt`), they show ten seconds after the GO at the soonest. That effect part runs below normal priority, the race runs meanwhile and the frame loop keeps the cores on a busy host, the track part keeps normal priority since it is the path to the GO.

What the stock does meanwhile: nothing new. `FUN_00479CC0`, the 0x0014 handler, closes the popups and runs the stage switch `FUN_00404410(0xB)` inside the packet handler, which runs the game stage init `FUN_004028C0` synchronously. No frame is drawn and no packet read until it returns, so the window keeps the last room frame. There is no loading stage and no loading art between the room and the race, the one `LOADING` string of the exe has no reader. After the init the stage draws the track with `Panel/Message/WaitPlayer.png` until the `0x003A` GO. Ours does the same without the freeze: `App` keeps the screens the race replaced and draws them, with no update, while `RaceScreen::holdsPrevious()` is true, so the room frame stays up and moves (`out_loading.png`, a capture one second into a load, `KNC_RACE_LOAD_DELAY=6000` stretches a load for that proof). The frames that come during the load wait in the race screen and play in their order after it, as the stock reads them after its init: the `0x003E` rows, the `0x000D` board, the `0x003A` GO. Every S2C `0x000D` gets its C2S `0x000D` answer once the track stands, as `FUN_00402210` answers it (docs/packets/opcodes/0x000D.md). The script `waitfor race` holds until the GO landed, so the race shots keep their place in the countdown whatever the grid delay of the server.

The client prints one `[time] race` line per step:

```
[time] race load thread started 1 ms after enter
[time] track nif 118 ms ... [time] race world scene 150 ms, col pieces, ini rows, col head, minimap
[time] race load thread world 183 ms textures 45 ms, 59 of 59 files read 231 parse 0 inspect 6
[time] race sim 10 ms, upload 6 ms, weather, gauge, countdown, gimmick rows
[time] race ready 297 ms after enter (at 5504 ms)
[time] race effects 729 ms on their thread in at 961 ms after enter
[time] race racer kart and driver Basic_1 Cosmo 3 ms
```

Measured on the sample race (`--state race`, `KNC_SAMPLE_TRACK=90` Toy Circuit or `10` Pinky Road), same machine, 2026-09-23:

| Track | Before, screen race enter | After, race ready | After, window frozen |
|---|---|---|---|
| Toy Circuit (Race_01, 90) | 24552 ms, first run of the day; 1502 ms with the pak hot in the file cache | 290 to 457 ms | never, enter 1 to 2 ms |
| Pinky Road (Forest_01, 10) | 43125 ms, first run; 1335 ms with the pak hot | 290 to 465 ms | never |

On the package server the gate saw 28761 and 26187 ms before (race_items, weather). The number moved with the file cache because the whole of it was one thing: the texture cache pointed at a second `PakReader` that byte scanned the 867 MB pak the first time a texture was not on disk (`GRASS.dds` of the wheel dust, the snow board of Toy Circuit), 54 textures read in 22971 ms of which one scan took nearly all. The client now points the texture cache at the pak index `AssetStore` read at the start (`AssetStore::readPakByName`, a lookup and one read by offset), and the track loader leaves it alone (`TrackSceneRequest::point_textures_at_pak` off).

What else went:

- The kart and the driver models are parsed once per process (`load_ghost_car` and `load_ghost_driver` keep a parse cache by file, paint, chassis and worn parts), the room built them before the race. A racer went from 40 to 118 ms to 3 to 7 ms.
- The car effect nifs were parsed on the main thread the first time an effect showed, in the race, and their folder was walked with `std::filesystem` for every effect of every car of every frame. They are parsed on the load thread and the walk is done once per name (`RaceEffects::cachedPath`).
- A capture encoded its PNG inside the frame, 150 to 270 ms. `PngScreenshotCallback` copies the pixels and encodes on its own thread.
- A frame over 250 ms prints its parts, `[time] frame 500 ms poll 0 net 0 update 4 draw 2 present 0 sleep 494 on race`. On a host at 70 to 97 percent CPU the gate still shows frames of 150 to 670 ms whose time is the sleep of the frame pacing, the event poll or the draw, the thread waits for a core, not our code. The same busy host read the track nif in 10.7 s instead of 118 ms, the race was then ready in about 6 s.

## Intro

`sub_4279B0` is the title stage. There is no movie: the pak and the client folder carry no `bik`, `avi`, `wmv` or `mpg` file, and the exe imports no video library and no DirectShow entry. The stage plays a nif, `Title/INTRO` (the string at 0x5A05E8), 401 blocks and 48 surfaces: seven background plates that scroll their u coordinate, four karts on transform tracks with their wheels, flames and shadows, a blur sheet flipped between `background6.dds` and `background7.dds` by a `NiFlipController`, and the `Login_THA_00` wallpaper plate that snaps on at 6.233 s.

The stage camera is the EngineDLL one: field 0.75 rad, near 10, far 10000, aspect 1, standing at the origin, looking along plus y with z up. The nif is scaled `1 1 1.335` and placed 1300 units along plus y. `sub_411FD0` fades the stage in over 500 ms, holds 5499 ms, then waits 999 ms and logs in with the launcher token, so the stage lasts about seven seconds. `sub_412110`, the window proc of the stage, routes only the mouse and the two launcher messages, so the stock has no skip key.

Ours plays the same nif with the same camera and the same seconds through `client/screens/LogoScreen`, on an empty scene with a flat ambient of 4 so every emissive surface saturates the way the fixed function device draws it. Any key or a click skips it, that part is ours. `--state intro` or `--stop-at intro` holds the stage for a capture, `KNC_INTRO_PARTS=<indices>` keeps only those surfaces of the nif, a capture aid for a plate that draws wrong.

All 48 surfaces draw since 2026-09-19. Two plates were dropped before: `Login_THA_00`, whose depth write hid the sky while its alpha controller kept it clear, and `background6`, the blur sheet, whose clear texels painted black. Both were one fault of the render module, the translucent queue ran near to far so every depth writing plate hid what stood behind it, see `RENDER_MODULE.md`. The blur sheet also needed the `NiFlipController` on a mesh part, it swaps `background6` and `background7` at 30 Hz now. `KNC_INTRO_DROP=1` leaves the two plates out again and draws the wallpaper from the overlay, the old frame for a comparison.

## Script harness

`--script <file>` drives a run like a hand on the mouse, one verb per line, a `#` line is a comment. The clicks and the keys go through the same entry points as the glfw callbacks (`App::mouseMove`, `App::mouseButton`, `App::key`, `App::charInput`), so a script proves the real path of a button. The coordinates are the 1024 by 768 stock ones. With `--screenshot` the window is hidden and the frames are paced at 25 a second, so `wait 25` is one second. The run ends on `quit` or when the lines run out, the exit code is 1 when an `expect` failed.

| Verb | What it does |
|---|---|
| `wait N` | N frames pass |
| `waitfor SCREEN [N]` | waits until the top screen is SCREEN and ready, at most N frames, default 250, prints ok or timed out. The race is ready once its track stands and the `0x003A` GO landed |
| `click X Y` | the cursor moves to X Y, the left button presses this frame and releases on the next |
| `rclick X Y` | the same with the right button |
| `key NAME` | a key press this frame and its release on the next, NAME is `escape` `enter` `tab` `space` `backspace` `up` `down` `left` `right` `f1` to `f12`, a letter, a digit, or the glfw code |
| `drag X1 Y1 X2 Y2 [left\|right\|middle] [N]` | the button presses at X1 Y1, the cursor walks to X2 Y2 one step a frame over N frames (default 10), the button releases on the last step, a room craft turn or pan is proved with it |
| `text WORDS` | one char event per utf8 character of the rest of the line, the focused input takes them |
| `shot NAME` | writes NAME.png next to the `--screenshot` path, or in the cwd without it |
| `expect SCREEN` | prints PASS or FAIL with the top screen name, the popups have their own names `makeroom` `escmenu` `help` `gameoption` `controloption` `confirm` `message` `messenger` `gacha` `password` |
| `quit` | ends the run after the pending shot is written |

## Screens and packets

The screens are the `ui_state_*.json` files under `Data/Public/UI`, the same format the ui editor reads: elements `image`, `button`, `text`, `input`, `list`, `panel`, `checkbox`, the button assets by the `_00 _01 _02 _03` suffix rule. The JSON files come from the stock init functions, the buttons and inputs carry their real spots, the images sit at the origin because the stock places them in its draw code. Every screen places those by hand from the decompiled draw functions, `_devclient_attic/KnC-new.exe.c`, the spots are in `UI_PARITY.md`. Images come from the pak first, then the `Data` folder, decoded through bimg. Every stock png is RGBA or RGB, bimg keeps the alpha, the sprite batch blends it. Text is Arial, the stock client draws all its text through GDI with a table of 48 Arial fonts of 14 to 29 px cells in the weights 400, 600 and 700 (`0x5CE5B0`, the face rule `sub_44D460` gives Arial for Eng and Frn), so `FontAtlas` reads `arial.ttf` and `arialbd.ttf` from the windows font folder with stb truetype, the Roboto header of the bgfx tree stays as the fallback. The stock size is the GDI cell height, a 15 px stock font is drawn at 15.
